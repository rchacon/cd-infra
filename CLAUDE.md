# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Architecture

Terraform IaC for `cd-platform`'s AWS deployment, split out of that repo (see its own `#5` issue) into a dedicated repo. Provisioned incrementally by component: `bootstrap/` (state backend, one-time), `networking/` (VPC/subnets/security groups), `rds/` (managed Postgres), `airflow-ecs/` (self-hosted Airflow, running `cd-etl`'s container as 4 independent ECS services on EC2), and eventually `cd-api/` (Lambda). See the root `README.md` for the architecture diagram, `terraform/README.md` for per-directory setup commands.

Each directory is its own Terraform root module with independent state (S3 backend, native `use_lockfile` locking, no DynamoDB table). Later directories read earlier ones' outputs via `terraform_remote_state`, using a gitignored `backend.hcl` for their own backend config and (where needed) a gitignored `terraform.tfvars` for the state bucket name -- both account-specific values that shouldn't be hardcoded into version-controlled `.tf` files. See `terraform/README.md` for the exact `backend.hcl`/`terraform.tfvars` contents to generate.

### Design decisions worth knowing before touching this repo

- **Security groups, not network ACLs, do all traffic control.** `networking/`'s three groups (`rds`, `airflow`, `lambda`) use standalone `aws_vpc_security_group_ingress_rule`/`egress_rule` resources rather than inline blocks -- required because `rds`'s ingress references `airflow`/`lambda` while their egress references `rds` right back, a mutual reference inline blocks can't express without a dependency cycle. The VPC module's default network ACL is explicitly *not* managed (`manage_default_network_acl = false`) -- adopting it would need `ec2:DescribeNetworkAcls`/`*NetworkAclEntry` IAM permissions for a resource this project doesn't otherwise use to enforce anything beyond what the security groups already do.
- **NAT gateway is on by default** (`enable_nat_gateway = true` in `networking/`, one shared gateway via `single_nat_gateway = true`) -- flipped on once self-hosted Airflow's EC2 instance (originally a single plain instance, `terraform/airflow/`, since decommissioned per `#42`; now `airflow-ecs/`'s) actually needed outbound internet (GHCR image pulls, package installs, SSM). It stayed off from `networking/`'s initial PR through `rds/`'s, per this project's "flip it on in whichever PR first needs it, not preemptively" policy.
- **RDS (`rds/`) is plain `aws_db_instance`, single-AZ, not Aurora** -- matches this project's current scale (a few thousand rows today; `bills`/`bill_subjects`/`roll_call_votes` later per `cd-platform#9`). `engine_version` is major-version-only (`"16"`, matching `cd-platform`'s local-dev `postgres:16`) with `auto_minor_version_upgrade = true`, so AWS resolves the current minor automatically rather than a hardcoded value going stale.
- **RDS's schema migrations are not Terraform-managed.** `cd-etl`'s own `alembic upgrade head` and Airflow's own metadata migrations both run automatically, baked into the `cd-etl` container's entrypoint on every start (per `cd-platform#26`) -- no manual step for either. RDS has no `docker-entrypoint-initdb.d` equivalent to create the sibling `airflow_metadata` database automatically, so `airflow-ecs/`'s EC2 instance (the only thing that can reach RDS, per its security group) bootstraps it itself: an idempotent `psql` step in `user-data`, using the RDS master/superuser credentials, creates `airflow_metadata` and a scoped least-privilege database role on first boot -- `cd-etl`'s container connects as that scoped role, never the master user, which is used only transiently for this bootstrap.
- **Two separate IAM surfaces exist for `airflow-ecs/`: the EC2 instance's own runtime role (Terraform-managed) and the `cd-terraform` deployer user's policy (Console-managed, empirical, per the IAM section below).** The instance role needs `secretsmanager:GetSecretValue`/`kms:Decrypt` to fetch its own secrets and the RDS master password at boot, plus `AmazonSSMManagedInstanceCore` for Session Manager access -- these are defined in `airflow-ecs/main.tf` since the instance needs them regardless of who's deploying. The deployer user's policy is the one built up empirically against real `AccessDenied` errors -- including, most recently, `iam:ListInstanceProfilesForRole`, needed to delete an IAM role during `#42`'s decommission of the original EC2 instance (AWS checks for attached instance profiles before allowing a role delete).
- **The Airflow UI (port 8080) has no public ingress, ever** -- the `airflow` security group defines zero ingress rules. Access is via SSM Session Manager port-forwarding (`aws ssm start-session ... --document-name AWS-StartPortForwardingSession`), not a VPN -- AWS Client VPN's per-subnet-association billing (~$72/mo) alone would dwarf this project's entire AWS spend for occasional admin access to one DAG's UI.
- **Every KMS key here is customer-managed, not the AWS-managed default** (the state bucket's key in `bootstrap/`, RDS storage's key in `rds/`) -- the point is requiring two independent grants (e.g. `s3:GetObject`/`rds` access *and* `kms:Decrypt` on that specific key) before someone can read the underlying data, rather than one over-broad IAM grant being sufficient on its own. Costs a flat ~$1/mo per key. If a new component needs its own KMS-encrypted resource, follow this pattern rather than defaulting to the AWS-managed key.
- **KMS alias operations need the alias ARN directly in `Resource`, not a `kms:AliasName` condition key** -- that condition key doesn't exist despite being a common assumption; alias-scoped IAM statements can't use condition keys at all, and alias operations independently need a separate statement granting usage on the underlying key resource too.
- **`cd-server/` (`server.civicdog.com`) runs on ECS's EC2 launch type, not Fargate** -- cheaper for an always-on workload, the same stance `airflow-ecs/` takes for Airflow's own ECS decomposition; a separate cluster/instance from that work, not shared. Its ALB target group uses dynamic port mapping (`hostPort = 0` in the task's `portMappings`, `target_type = "instance"`) rather than a fixed container port, so more tasks can land on the same instance later without an SG/target-group change. `cd-server` reaches `cd-api` by invoking its Lambda **directly via `boto3`** (an IAM `lambda:InvokeFunction` grant), not over HTTP/API Gateway -- no network path between the two components is needed.
- **An ALB's ACM certificate is regional, unlike every other custom domain in this repo.** `cd-api`'s/`cd-webapp`'s custom domains are all CloudFront-backed (API Gateway `EDGE`, Amplify, Cognito Managed Login), which is what actually forces those certs into `us-east-1` regardless of the resource's own region -- an ALB has no CloudFront in front of it, so `cd-server/`'s cert for `server.civicdog.com` is requested in `var.aws_region` directly, no aliased `us_east_1` provider needed.
- **`airflow-ecs/` avoids a migration-race problem via an ECS task definition's `entryPoint` override, not a `cd-platform` code change.** `cd-etl/entrypoint.sh` runs `airflow db migrate`/`alembic upgrade head` unconditionally, before even looking at its arguments -- so naively running `scheduler`/`triggerer`/`dag-processor`/`api-server` as 4 independent services off that image would race migrations against RDS on every task start. ECS task definitions can override a container's `entryPoint` independently of the image's baked-in `ENTRYPOINT ["/entrypoint.sh"]`; pointing the 4 long-running services straight at `airflow` (already on the image's own `PATH`) skips the entrypoint script -- and its migration block -- entirely. A 5th task definition (`migrate`, invoked ad hoc via `run-task`, never a service) keeps the default entrypoint with a `command = ["create-admin-user"]` override, so migrations still run once and then it hits `cd-etl/entrypoint.sh`'s dedicated `create-admin-user` subcommand (which also idempotently provisions/resets the FabAuthManager admin account, `cd-platform#74`/`#31`/`#75`) instead of falling through to `airflow standalone`. Worth remembering as a reusable pattern for any future component sharing an image whose entrypoint does unconditional setup work.
- **`airflow-ecs/`'s FabAuthManager admin password is Terraform-generated and durable, not the auto-generated one `SimpleAuthManager` used to log in plaintext.** A `random_password` (alphanumeric-only, same "sidesteps CLI-arg-quoting entirely" reasoning as this module's own `cd_etl_app` password) stored as its own Secrets Manager secret, injected into the `migrate` task only -- the 4 long-running services never provision the admin account themselves, only the one-shot `migrate` task's `create-admin-user` invocation does.
- **`airflow-ecs/` originally ran *alongside* a single plain EC2 instance (`terraform/airflow/`), not as a replacement for it, until validated -- that instance has since been decommissioned (`#42`).** Both were safe to run concurrently against the same RDS `airflow_metadata` database while validation was pending -- Airflow's scheduler HA design (row-level locking) exists precisely to let multiple scheduler processes coexist without duplicate task execution. `airflow-ecs/` originally reused that instance's `airflow` security group, KMS key, and Secrets Manager secrets via `terraform_remote_state`; once `congress_members_etl`/`bills_etl` were confirmed completing successfully on the new ECS scheduler, the KMS key and both secrets (plus the `random_password` behind one of them) were moved into `airflow-ecs/`'s own state via `terraform state mv` (not recreated -- same live ARNs, same already-set `cd_etl_app` Postgres password), and the original instance + its supporting IAM were destroyed. `house_votes_etl` stays paused -- a separate, known issue (its `fetch_member_votes` task is memory-heavy enough to get OOM-killed inside the scheduler's `LocalExecutor` process), not a blocker for the decommission.
- **`cd-server/`'s `cd_customers` database is bootstrapped the same way `airflow-ecs/`'s `airflow_metadata` one is** (`cd-infra#48`) -- its ECS EC2 instance's own `user-data` does the idempotent `psql` bootstrap (RDS master credentials, used only transiently, create `cd_customers` + a scoped `cd_server_app` role) rather than anything Terraform-native, since RDS still has no `docker-entrypoint-initdb.d` equivalent. The role's password is a `random_password` in its own Secrets Manager secret (reusing `cd-server/`'s existing KMS key rather than provisioning a second one), injected into the task definition via ECS's native `secrets` block (`PGUSER`/`PGPASSWORD`, `:key::` JSON-field syntax) -- the task execution role, not the task role, needs `secretsmanager:GetSecretValue`/`kms:Decrypt` to resolve it. This needed a new `networking/` security-group hole too: `cd_server`'s SG had no RDS egress (and `rds`'s SG no ingress from `cd_server`) since it had no database wiring when first created. Cognito (`COGNITO_USER_POOL_ID`/`COGNITO_REGION`/`COGNITO_CLIENT_IDS`) is wired up alongside it, read via a new `terraform_remote_state` on `cd-webapp/` -- none of the three are secret, so they're plain task-definition `environment` entries, not `secrets`; `COGNITO_CLIENT_IDS` is comma-joined from both the prod and local-dev App Clients sharing that one User Pool.
- **`airflow-ecs/`'s and `cd-server/`'s GitHub OIDC deploy roles (`airflow_deploy` `cd-infra#43`, `cd_server_deploy`) now have the same shape** -- both do a migrate-then-deploy per release. Same trust policy (`AssumeRoleWithWebIdentity`, `Federated` principal on `var.github_oidc_provider_arn`, `sub` via `StringLike` on `ref:refs/tags/cd-etl-v*` / `cd-server-v*`), and both grant `ecs:RunTask` on the one-shot migrate task definition's *family* wildcard (`arn_without_revision` + `:*`, not a pinned revision -- the workflow runs whichever revision is current at deploy time, not the one that existed at `terraform apply`), scoped by an `ecs:cluster` condition; `ecs:DescribeTasks` on the cluster's task namespace (for `aws ecs wait tasks-stopped` + reading the exit code); `iam:PassRole` on the migrate task's execution/task roles (condition-scoped to `iam:PassedToService = ecs-tasks.amazonaws.com`, required by `RunTask` itself); and `ecs:UpdateService`/`DescribeServices` to force-redeploy afterward (`airflow_deploy` covers all 4 services, `cd_server_deploy` the one). `cd_server_deploy` gained the `RunTask`/`PassRole`/`DescribeTasks` half in `cd-infra#67` (before that it only ever called `UpdateService`). The role name `cd-platform-airflow-deploy` is load-bearing: `cd-platform#80`'s workflow hardcoded that exact ARN as a placeholder before the role existed.
- **`cd-server/` deploys are rolling / zero-downtime (`cd-infra#67`), not the stop-then-start they were.** The ECS service is a surge deployment (`deployment_minimum_healthy_percent = 100` / `deployment_maximum_percent = 200`) with a 30s target-group `deregistration_delay` and the circuit breaker (`cd-infra#66`) -- previously `0/100` + a ~300s drain gave every deploy a ~5-6 min ALB 503. Surge briefly runs two app tasks, so `alembic upgrade head` can't live in every task's entrypoint anymore: a dedicated one-shot `cd-platform-cd-server-migrate` task (default `/entrypoint.sh` + `command = ["migrate"]`) owns it, the long-running service task sets `CD_SERVER_MIGRATE_TASK=1` (which `entrypoint.sh` reads to skip the on-boot migrate and just exec the uvicorn `CMD` -- no `entryPoint` override needed, unlike `airflow-ecs/`, because cd-server's `entrypoint.sh` does nothing but that conditional migrate), and `cd-platform`'s `cd-server-deploy.yml` runs the migrate task and asserts exit 0 before `update-service`. Same one-shot-migrate-task split as `airflow-ecs/`. App-side landed in `cd-platform#133` (adds the `migrate` subcommand, the `CD_SERVER_MIGRATE_TASK` opt-out, and a `pg_advisory_lock` in `migrations/env.py`). Rolling deploys mean old app code briefly runs against the new schema -- migrations must be expand/contract, documented in `cd-server/README.md`.
- **`cd-server/`'s task role gets Bedrock `InvokeModel` for the AI voting-record summaries (`cd-infra#69`)** -- the cd-server analogue of `#54`/`#55`/`#58` (cd-etl/cd-api Titan embeddings for `cd-platform#9`). `summarizeVotingRecord` (`cd-platform#161`-`#163`) calls Bedrock's Converse API, which authorizes as `bedrock:InvokeModel` (no separate `bedrock:Converse` action). Unlike the Titan grants -- a bare on-demand model id, one region -- Claude on Bedrock needs a **cross-region inference profile** (`us.`-prefixed), so the policy lists both the account-qualified `inference-profile/` ARN in `var.aws_region` *and* the bare `foundation-model/` ARN in every region the US profile routes to (`us-east-1`/`us-east-2`/`us-west-2`), all derived from one `local.bedrock_chat_profile_id` (currently `us.anthropic.claude-haiku-4-5-...`; that local is the entire switch for changing model/tier). **Model access itself is a manual Bedrock Console step in each of those three regions** -- Terraform can't manage it, same "empirical, out-of-band" character as the `cd-terraform` IAM policy. Egress was already covered: `networking/`'s `cd_server_https` rule permits 443 to `bedrock-runtime` via NAT (only its comment/description changed). The task def gains `BEDROCK_CHAT_MODEL_ID` (the profile id) and `AWS_REGION` (`cd-lib/bedrock.py` reads it explicitly, `NoRegionError` at client construction otherwise, with a `us-west-2` fallback that happens to match) -- `BEDROCK_CHAT_MODEL_ID` must be live *before* cd-platform's GraphQL-wiring deploy, since `get_bedrock_chat_client()` is a fail-fast `RuntimeError` at import when it's unset in a non-`local` env (same failure mode as `#48`). Bedrock is pay-per-invocation (~$0.005/summary at Haiku 4.5, output capped server-side at 1024 tokens) -- no standing cost, so not in the Cost section.

## IAM

The `cd-terraform` IAM user's policy is hand-managed in the AWS Console (not Terraform-managed), attached via a group, deliberately avoiding `AdministratorAccess`/`PowerUserAccess` (the latter excludes `iam:*`, which this project's future EC2/Lambda execution roles will need). It's been built up **empirically, one real `AccessDenied` error at a time** across `networking/` and `rds/` -- run `terraform plan`/`apply`, let AWS name the exact missing action, add it to the Console policy, retry. Don't try to pre-write a "complete" policy from memory or documentation; AWS's actual error messages are more reliable than guessing, and this project has been burned before by KMS-specific assumptions that turned out wrong (see the alias-ARN note above).

## Cost

With `enable_nat_gateway = true` (current default, since self-hosted Airflow first needed it), the running total is roughly: `bootstrap/`'s KMS key (~$1/mo) + `rds/`'s KMS key (~$1/mo) + the `db.t4g.micro`/20GiB gp3 RDS instance (~$12-15/mo) + the single shared NAT gateway (~$32-33/mo) + `airflow-ecs/`'s KMS key (~$1/mo) + its `t3.medium` EC2 instance (~$30/mo, x86_64 -- cd-etl's GHCR image is amd64-only) + `cd-server/`'s KMS key (~$1/mo) + its `t3.small` EC2 instance (~$15/mo, bumped from `t3.micro` in `cd-infra#67` for rolling-deploy surge headroom) + its ALB (~$16-20/mo, mostly the flat hourly charge, LCU usage is negligible at this project's traffic) + its `cd_customers` DB-credentials Secrets Manager secret (~$0.40/mo, no new KMS key -- reuses `cd-server/`'s existing one) + small CloudWatch Logs charges for both `cd-server/` and `airflow-ecs/` (Service Connect itself is free). `airflow-ecs/`'s `t3.medium` was briefly additive on top of the original `airflow/`'s `t3.small` (~$15/mo) during its parallel-validation window -- that instance and its KMS key were decommissioned (`#42`) once `airflow-ecs/` was confirmed working, landing at the totals above rather than the two running side by side. VPC/subnets/route tables/IGW/security groups are free.

## Standing agreement on `terraform apply`

`terraform plan` freely. Always get explicit confirmation before `terraform apply` -- it creates real, billable AWS resources.

## Git conventions

PRs are merged with a merge commit (`gh pr merge --merge`), not squash or rebase -- preserves the individual commit history from the PR branch. After merging, delete the branch both locally and remotely (`gh pr merge --merge --delete-branch` does both in one step).

When addressing review comments on an open PR, break the fixes up into separate commits along logical lines (one commit per distinct issue/fix, not one commit for everything) rather than a single catch-all commit, and reply to each review comment on GitHub referencing the specific commit hash that addressed it (e.g. "Fixed in `abc1234`.") -- keeps the review thread traceable to the exact change that resolved it, rather than a generic "addressed" reply pointing at the whole PR.

When *submitting* a code review on a PR, post each finding as its own separate inline review comment (anchored to the specific file/line via `gh api repos/{owner}/{repo}/pulls/{number}/comments`, not a single bundled `gh pr comment`) -- a combined comment listing every finding only supports one flat reply thread, making it impossible to reply to (or resolve) individual findings separately later.

## Commands

See `terraform/README.md` for the full per-directory setup (backend.hcl/terraform.tfvars generation, init/plan/apply). Quick reference, validating without AWS credentials (same checks CI runs):

```bash
terraform fmt -check -recursive terraform/
for dir in $(find terraform -name '*.tf' -printf '%h\n' | sort -u); do
  terraform -chdir="$dir" init -backend=false -input=false
  terraform -chdir="$dir" validate
done
```

CI (`.github/workflows/terraform-checks.yml`) runs `fmt`/`validate` (directory-discovery based, so new `terraform/*` directories are picked up automatically) plus a Trivy IaC security scan on every PR.
